# スキルの取り込み方を決める

指定された移行元スキルを、ローカルの作業手順に合う小さなスキルセットへ取り込む。基本方針は、スキルの数を増やしすぎないこと。

**必須サブスキル:** `SKILL.md` を作成または編集する前に、必ず `authoring-skills` を使う。このスキルは、採用・調整・吸収・却下の判断を扱う。草稿作成、RED の場面、`description` の品質、検証記録は `authoring-skills` の責務とする。外部の候補を評価するときは `references/adoption-rubric.md` を使う。

## 入力

必要な情報だけを読む。

- 移行元スキル: ローカルパス、インストール済みスキル、URL、貼り付けられた本文
- 対象にする作業手順の制約と、既存のプロジェクト指示
- すでに採用済みのスキルと、リポジトリ内だけで使うスキル
- 明示された検証条件

## 判断

移行元スキルごとに分類する。

| 判断 | 使う条件 |
| --- | --- |
| `adopt as-is` | 単独で成立しており、互換性があり、対象の作業手順と衝突しない。 |
| `adapt` | 中核となる手順には価値があるが、移行元の慣習、ツール構文、対象範囲を変える必要がある。 |
| `absorb` | 小さな考え方だけが有用で、新しいスキルを作るより既存スキルに加える方がよい。 |
| `reject` | 重複している、一回限りである、広すぎる、特定ツールに寄りすぎている、またはコンテキスト量に見合わない。 |

`adapt` よりも `adopt as-is` または `absorb` を優先する。単独で繰り返し使う価値がある場合だけ、新しいスキルを作る。

## 取り込みルール

- 移行元スキルの有用なふるまいを残す。偶然の命名、ディレクトリ構成、ツール前提は残さない。
- 対象の作業手順がすでに使っている場合を除き、セットアップ手順、非公開の慣習、ライフサイクル管理の状態遷移は削る。
- 競合するスキルを並べて残すのではなく、重複する起動条件を統合する。
- 可能なら、作成後の `SKILL.md` は 500 語未満に保つ。
- `description` には手順の要約ではなく、そのスキルをいつ使うかを書く。
- ふるまいを変えるスキルには、出力形式、停止条件、検証シナリオを追加する。
- 新しい評価者が実際にシナリオを実行していない限り、実証的に検証済みだと主張しない。

## 手順

1. 移行元スキルを読み、それが守っている再利用可能なふるまいを特定する。
2. すでに採用済みのスキル、リポジトリ内だけで使うスキルと比較する。
3. 編集前に判断表を作る。
4. 最小の変更で反映する: `adopt as-is`、`absorb`、`adapt`、`reject`。
5. 残すスキルについてだけ README やカタログを更新する。
6. 検証状態を記録する: `untested`、`structurally reviewed`、`scenario-tested`。

## 出力

```markdown
## 判断表
| 移行元スキル | 判断 | 理由 | 反映先 |
| --- | --- | --- | --- |

## 変更
- <スキルまたはファイル>: <何を、なぜ変えたか>

## 却下
- <移行元スキル>: <理由>

## 採用根拠
- 移行元のスナップショット:
- 確認した判断軸:
- 重複や互換性の根拠:
- ライセンスと由来:

## 検証
- 構造チェック:
- シナリオの状態:
- 実証的検証の状態:
```

## よくある誤り

- 1 段落だけ吸収すればよいのに、スキル全体を fork する。
- 元のスキルに書かれていたという理由だけで、移行元固有のセットアップを残す。
- `description` の重複を増やすだけのルータースキルを作る。
- 静的レビューしかしていないのに、検証済みだと言う。
