# 既存資料を使った設計

これは、既存資料を踏まえて進める設計の会話である。プロジェクト固有の用語集ファイルを必須にせず、ドキュメントとコードに照らして計画を厳しく検討する部分だけを残す。

## 最初に読む

関連する情報源だけを読む。

- `README.md`、`CONTRIBUTING.md`
- 存在する場合は `docs/adr/`
- 存在する場合は `docs/specs/` または `specs/`
- 紐づいた GitHub または Linear の issue
- 現在の設計上の問いに答えられるコード

## 境界

問題が不明確な場合は、先に `framing-problems` を使う。モジュール境界、インターフェース、テストしやすさが主な論点の場合は `reviewing-architecture` を使う。

## 会話ルール

- 一度に 1 つの質問をする。
- 各質問には、推奨回答がある場合それを含める。
- コードやドキュメントで答えられる質問は、質問するのではなく調べる。
- 根拠なしに方向性を推奨しない。根拠が足りない場合は、質問する、調査する、または小さな試作を提案する。
- あいまい、または複数の意味に取れる言葉は確認する。
- 具体的な場面を使って、境界と端のケースを確認する。
- ユーザーの説明、既存ドキュメント、コードの矛盾を表に出す。
- 主要な指摘それぞれについて、それを支える資料またはコード上の観察を示す。
- 実際のトレードオフがある場合は、妥当な代替案を 2-3 個比較し、却下した案がなぜ負けるかを明示する。
- プロダクト判断、技術判断、実装詳細を分ける。

## 手順

1. 検討する設計上の問いを述べる。
2. その問いに必要な資料だけを調べる。
3. 2-3 個の具体的な場面に照らして設計を確認する。正常系、端のケース、失敗または戻し方を含める。
4. 影響を分類する。プロダクトのふるまい、データ/API 契約、技術設計、実装詳細、資料更新のどれか。
5. 最小のブロッキング質問を聞く。根拠が十分なら推奨判断を述べる。
6. 判断、未解決の質問、次に作る資料が明確になったら止める。

## ADR の扱い

以下がすべて当てはまる場合だけ ADR を提案する。

1. その判断を戻すのが難しい、または高コストである。
2. 将来の読者が、文脈なしでは意外に感じる。
3. 妥当な代替案の間に実際のトレードオフがあった。

条件が 1 つでも欠ける場合は、判断を仕様、issue、タスクノート、または最終まとめに留める。

## 出力

最後はこの形にする:

```markdown
## 決定
- <決定と理由>

## 未解決の質問
- <質問、担当者、ブロックしているかどうかとその理由>

## 代替案
- <検討した案、トレードオフ、採用/却下の理由>

## 影響
- <プロダクトのふるまい、技術設計、実装、資料の何が変わるか>

## リスク
- <リスクまたはトレードオフ>

## 根拠
- <資料パス、issue、ADR、またはコード上の観察>

## 次の成果物
<issue | spec | ADR | research | prototype | implementation | no action>
```
